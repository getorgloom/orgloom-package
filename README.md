# Org Loom Salesforce package

The canonical development source is `orgloom-package/` in the main Org Loom repository. This directory is published separately to `getorgloom/orgloom-package`; make changes in the main repository.

A Salesforce-hosted build. The hosted app and VS Code extension are unchanged. The managed release is composed as the next version of the existing `orgloom` package; see [PACKAGING.md](PACKAGING.md). This is not an AppExchange review approval or a claim of feature parity.

**Source published for inspection.** The proprietary native code is all rights reserved; publication does not grant permission to deploy or operate Org Loom. Use of the managed package requires separate authorization under an applicable license agreement. See [LICENSE](LICENSE) and [component licensing](LICENSING.md).

## Architecture

Lightning tab → Visualforce → pinned canvas frontend in a static resource → JavaScript remoting → Apex. The current Salesforce session authenticates requests. Business operations use user-mode queries/DML and sharing checks. No Org Loom server, browser OAuth token, external AI client or Salesforce REST self-call participates.

The canvas renderer, editor, Browse, upload review and save/load UI are reused. Native adapters translate requests to Apex. AI, MCP and live presence modules are excluded. Compatibility interfaces perform no synchronization.

## Implemented

- Team feature definitions in custom metadata, grants through Custom Permissions/Permission Sets, org restrictions through policy records, and an admin page. These grant app capabilities, never business object/field permissions. Namespaced builds also check the current user's Salesforce managed-package license; pricing, LMA configuration and distribution are separate release tasks.
- Dynamic discovery of readable/queryable standard and custom objects with record IDs. Hidden objects, custom settings, custom metadata, platform events, big objects and internal native storage are excluded. Accessible field describes, draft creation and edits, Browse/filter/selected-record loading, and SOQL import capped at 500 total records (including child-query results), with relationships restored between imported records. Selected queries execute in user mode before readable fields are hydrated; include Id in each SELECT. Aggregate and locking queries are rejected.
- Parent/child schema graphs, related-record counts/loading (up to 200 records), lookup search and record refresh. Reads use user mode; relationship requests also require access to the referenced parent. Count probes are split into transactions of at most 25. Required lookup filters remain enforced by Salesforce on upload; the search does not yet reproduce UI API lookup-filter suggestions.
- Uploads of up to 500 records across 20 object types, in atomic batches of at most 200: bulk create/update/delete and external-ID upsert, parent-first linked drafts and child-first deletion. Nullable reference cycles use a second update where Salesforce permits them. User-mode writes, stale-record checks, rollback on failure and durable attempt receipts remain enforced. Customer automation and governor limits can still reject smaller uploads. Independent groups use separate transactions with explicit partial-success results. Durable server plans prevent changed payloads from being replayed; unconfirmed outcomes stop later batches. Upserts resolve accessible matches at planning, recheck them before execution, and roll back unexpected late matches. Duplicate overrides use USER_MODE DML options for inserts/updates; new external-ID upserts cannot combine with an override and fail explicitly. Salesforce DML errors retain actionable field/error codes in the immediate response; durable failure receipts omit field values.
- Encrypted canvas save/open/delete, up to 500 records and 1 MB serialized payload. Opens filter records, field values, request fields, metadata defaults and relationships against current Salesforce access. Editors can save visible changes while server-side merging preserves hidden content. Contributors can fill visible requests. Saves recheck current permissions, lease and version; guessed hidden identities/fields are rejected. Removing a visible card with hidden content/connections retains that card in the saved revision. Existing-record fulfillment of a request with hidden content requires its owner; visible new-record fields can still be completed. Owner-only saved-canvas deletion removes the encrypted revisions, not business records or Recall history.
- Exclusive editing with a two-minute lease and 30-second heartbeat. A second session asks before takeover. Old sessions cannot save/upload and show an ended-session overlay at the next heartbeat. Switching canvases releases the previous lease. Takeover loads the last saved version, not unsaved edits.
- Same-org JSON canvas import/export and linked CSV import/record export reuse the shared parsers, mapping dialogs and serializers. File imports require bulk-edit access; exports recheck their feature grants. **Tools → Export for migration…** defaults the normal JSON export's migration checkbox on. Marked exports, or files identifying a different source org, open staged destination reconciliation. Source IDs and lookup values are cleared, canvas relationships are rebuilt, and applying the reviewed plan replaces the canvas; cancellation preserves it. Unidentified files and foreign saved-snapshot formats remain rejected. CSV external-ID upsert is enabled. Available active record types and the current user default are normalized for the shared editor.
- Run script and auto-fill reuse the pinned local interpreter, sample generation and undo behavior. Separate feature grants apply. Saved-canvas use requires an owner/editor lease; contributor/viewer access is denied. Async completion checks the canvas and editing session again before mutation. Scripts do not receive an Apex or network execution channel.
- Memory-only canvas data in the browser. Reload discards unsaved work; only scoped onboarding flags persist locally. Production use is supported by the managed build, subject to package validation and release. There is no test-org bypass of access or business-data permissions.

- Recipient sharing and record/field requests: owners choose Viewer/Contributor/Editor access for active Salesforce users. Recipients open Saved canvases or a copied link; no email is sent. Contributors submit only requested fields or fulfill whole-record requests by creating a draft or choosing an accessible existing record. Submissions create an encrypted saved revision, not Salesforce business writes. A contributor reloads the revision after submission. Revocation and role changes invalidate an active recipient lease.
- Upload history and Recall: encrypted before/after field snapshots are captured in the same atomic transaction as the upload. The uploader can preview current values, restore selected fields, or delete eligible creations. Later edits require explicit override selections after review; a changed review token rejects writes. Creation drift includes field values, not just timestamps. Related records outside the deletion selection block Recall. Deleted records cannot be restored, and customer automation/governor limits can reject a Recall. Forget hides the history entry while retaining the upload idempotency receipt and encrypted snapshot.
- Paste a Salesforce record URL: copy a link from the connected org, click an empty area of the canvas, then press Ctrl+V (Cmd+V on macOS). Saved values load through Browse permission checks and Apex USER_MODE. Existing cards are selected without overwriting edits; new cards use the existing import layout. Input fields and dialogs keep their ordinary paste behavior. Canvas card copy/paste remains available using a session-only clipboard marker containing no record values. No background clipboard access or extra panel is used. The experimental drag handlers, diagnostics, styling and Workspace API bridge have been removed.
- Full page layouts through **Org Loom Canvas**, with exact-origin/source-checked messages between the Lightning wrapper and Visualforce. Unsupported UI API objects fall back to accessible fields. Record-type and dependent-picklist values use Salesforce UI API and fresh permission-filtered describes.

These workflows are implemented; full hosted parity is not claimed. The object catalog is broader, but field types outside the supported scalar/reference types and object-specific query constraints still need coverage. Unsupported actions stay disabled or fail explicitly. See [ARCHITECTURE.md](ARCHITECTURE.md) for accepted scope.

## Encryption boundary

The existing package KEK implementation is pinned under `vendor/key-service` and adapted to isolated native names. Each version uses a random AES-256 data key, managed IV and encrypt-then-MAC authentication bound to org, canvas and revision. The reused KEK service wraps the data key. Files contain encrypted envelopes, not plaintext canvas values. Keys and decrypted payloads are not logged.

The Apex AES-CBC/HMAC envelope differs from the hosted Node format; existing hosted ciphertext is not interchangeable. Canvas metadata such as title, owner and version IDs is not encrypted.

`OrgLoomNativeCanvases` intentionally uses system mode for private application records and encrypted Files, after explicit capability, owner/recipient, lease and version checks. Business access is separately enforced in user mode. Users receive no direct CRUD on internal storage/key objects. A protected setting is **not** a managed-package isolation boundary in this unpackaged UAT project: org administrators remain trusted. Namespaced packaging and security review are release requirements.

## Refresh recovery

Native refresh recovery stores private encrypted checkpoints in Salesforce, separate from explicit saves. Real session storage holds an opaque recovery identifier and canvas-scoped editing-session metadata so the same tab can reopen a saved canvas after refresh. A browser Web Lock prevents a duplicated tab from silently reusing that editing session. Shared-runtime record caches remain in memory; record values and Salesforce credentials are not stored there.

- `OrgLoomNativeRecovery` checks current-user ownership, app access, org identity, record/field permissions, saved-canvas role, revision and lease. Restoration rotates writer/session capabilities; another tab, revoked grant or newer saved revision cannot silently overwrite the resumed work. Hidden shared content remains in the canonical saved revision.
- One current encrypted File per editing session (including unsaved canvases), up to ten active sessions per user. Atomic replacement deletes the superseded document instead of accumulating versions. A failed write preserves the last confirmed snapshot. Limits match native saved canvases: 500 records / 1 MB serialized payload.
- Poll every two seconds, checkpoint after two seconds without a changed snapshot or approximately ten seconds of continuous changes, plus server time. The status reports failures. No async unload guarantee. Restore/discard is offered after refresh. A blocked browser session-storage API prevents reliable refresh lookup and reports that limitation.
- Confirmed saves/discards remove the encrypted checkpoint; small tombstones block delayed writes. A pre-upload checkpoint is retired before the first business write, and checkpointing resumes after confirmed upload results reach the canvas. In-progress migration reconciliation is excluded. Recovery is not a replacement for explicit saves or upload-result reconciliation.
- Checkpoints expire 24 hours after their last successful write. `OrgLoomNativeRecoveryCleanup` runs daily at 2 a.m. in the scheduling user’s time zone (scheduled by package installation), rechecks expiry under lock, and deletes expired documents and metadata in batches of 25. Salesforce recycle-bin and backup rules still apply; this is not a permanent-erasure promise. For an unpackaged deployment, an app admin must run `OrgLoomNativeRecoveryCleanup.ensureScheduled()` once; it also replaces an older hourly schedule with the daily schedule.
- Encrypted snapshots use the existing AES-256-CBC/HMAC envelope. A 1 MB serialized payload is approximately 1.34 MB after encoding, before metadata/recycle-bin overhead and temporary replacement overlap. Recovery rows contain identifiers, hashes and timestamps, not record values.

## Build and deploy

```powershell
npm ci
npm test
npm run build
sf project deploy start --target-org orgloom-uat --source-dir force-app --test-level RunSpecifiedTests --tests OrgLoomNativeControllerTest --tests OrgLoomNativeAccessTest --tests OrgLoomNativeUploadTest --tests OrgLoomNativeBrowseTest --tests OrgLoomNativeCryptoTest --tests OrgLoomNativeKekTest --tests OrgLoomNativeCanvasesTest --tests OrgLoomNativeReadsTest --tests OrgLoomNativeQueryTest --tests OrgLoomNativeSharingTest --tests OrgLoomNativeMigrationTest --tests OrgLoomNativeHistoryTest --tests OrgLoomNativeRecordLinkTest --tests OrgLoomNativeUpsertTest --tests OrgLoomNativeProjectionTest --wait 5
sf apex run --target-org orgloom-uat --file scripts/grant-access.apex
```

The grant script assigns implemented native capabilities/admin access to the CLI-authenticated UAT user only, without changing business object/field permissions. Admins manage feature assignments in **Org Loom Team Administration**. Feature settings are private per-user records, not additional permission sets. New users have no features until an administrator enables them. Run `scripts/grant-features.apex` separately after `scripts/grant-access.apex` to enable features for the CLI-authenticated UAT user.

Open **Org Loom Canvas** in Lightning for the layout wrapper. The separate **Org Loom Canvas (Standalone)** navigation tab is retired; the underlying Visualforce page remains the renderer used by the Lightning wrapper. The released tab definition remains only in managed compatibility metadata pending Salesforce deletion enablement; it is hidden for the UAT administrator. Salesforce supplies CSRF-confirmed Visualforce navigation. Bare Visualforce URLs without that confirmation are intentionally rejected. **Canvases** in the canvas toolbar opens the saved-canvas browser.

The build verifies original canvas and key-service hashes and packages the shared JavaScript unchanged. Native platform choices are registered in `web/platform.js` through the core's supported hooks; there are no canvas source-text build patches. Native adapters live in `web`, Apex in `force-app`, feature definitions in `config/features.json`. Run the explicit generation scripts when changing generated metadata. Do not edit the vendored frontend. Update the reviewed runtime snapshot with the canonical repository's `tools/canvas-runtime/export.mjs`; working-tree snapshots are explicitly identified in the manifest.

## Administrative activity

The Org Loom Activity tab requires Org Loom Admin (checked again on every Apex request). It records successful upload batches, recalls, saved-canvas creation/update/deletion, access changes, request submissions, record refreshes, and summarized rejections. Events are written by the corresponding Apex operations, with success entries committed or rolled back alongside the changes. Idempotent upload and recall retries do not repeat success events. The private activity object contains only actor/time, action/status, reference IDs, and fixed summaries/counts; no record values, canvas titles, raw errors, or OAuth credentials. Canvas users retain personal Upload history separately.

Filters support action, status, user and inclusive local dates, with stable cursor pagination (50 rows). Events start with this version and are not backfilled. Entries are retained in Salesforce until removed through the customer's retention process; neither recovery cleanup nor Forget removes them. There is no workspace/billing activity feed.
